How This Was Built

The engineering behind the dashboard — how a sighting report gets from NUFORC's website onto this page.

Dashboard How This Was Built

The pipeline, in three steps

  1. 1

    Scrape

    A Selenium script drives a real Chrome browser through the NUFORC.org paginated public sighting index, page by page, pulling every report into a Pandas table.

  2. 2

    Clean

    Dates get parsed and validated, obviously mistyped entries (a sighting "year" of 1400, for instance) get filtered out, and geographic fields get normalized.

  3. 3

    Store & publish

    Everything is written to a Postgres database. A separate export script then aggregates it down into the small JSON files this site actually reads — the public page never connects to the database directly.

Problems solved along the way

Getting past Cloudflare's bot detection

Problem: NUFORC's site sits behind Cloudflare's bot protection, which blocked a standard Selenium browser outright — the scrape couldn't even get past the front page.

What I did: switched to undetected_chromedriver, which strips out the automation fingerprints Cloudflare checks for, and paired it with a persistent browser profile so that once a verification challenge is cleared by hand, that trust carries over to future runs instead of re-challenging every time.

Why it matters: Cloudflare (or something like it) sits in front of a lot of public data sources. Getting past it is the difference between "the pipeline exists" and "the pipeline actually runs."

An environment version-mismatch cascade

Problem: Python, Chrome, and ChromeDriver don't always agree with each other, and I hit that from three directions in a row: Python 3.12 removed a module (distutils) that a dependency still imported, the installed Chrome version and the auto-downloaded ChromeDriver version silently mismatched, and a stale cached driver kept getting reused even after that mismatch was fixed.

What I did: wrote a small compatibility shim to cover the missing module, added a helper that reads the installed Chrome version straight from the Windows registry and passes it through explicitly instead of trusting auto-detection, and now clear the driver cache before every run.

Why it matters: this class of bug — the code didn't change, but the environment around it did — is one of the most common reasons a working script quietly stops working later. The fix here generalizes well past this one project.

A dependency update broke parsing overnight

Problem: a pandas version upgrade changed how it accepts raw HTML for parsing. The scrape step started failing with a FileNotFoundError — because pandas was now trying to interpret the scraped HTML string as a file path.

What I did: wrapped the HTML string in io.StringIO(...) before handing it to pandas.read_html().

Why it matters: a small fix, but a good example of a confusing failure mode worth recognizing quickly: nothing in my code changed, a dependency's behavior did.

Moving from a CSV file to a real database, safely

Problem: the pipeline originally wrote its results to a local CSV file, which doesn't support the kind of live, queryable dataset this dashboard needs.

What I did: switched the write step to Postgres via SQLAlchemy, and moved the database password out of the script entirely — it's read from an environment variable at runtime instead of being hardcoded.

Why it matters: basic credential hygiene, but the kind that's easy to skip on a personal project and easy to regret later.

Deciding what counts as "real" data

Problem: while building the charts on this site, a few dozen reports turned up with obviously mistyped years — 1400, 1639, 1714, and others clearly aren't real sightings from those centuries.

What I did: rather than silently dropping them or silently keeping them (which would stretch the yearly chart across a mostly-empty 600-year range), the export script filters anything before 1900 and logs exactly which years and how many rows were excluded, so the decision is visible rather than buried.

Why it matters: cleaning real-world data always means making judgment calls like this one — the goal is making them deliberately and leaving a trail, not pretending the data arrived clean.

What's still rough

Built in the open, including the parts that aren't finished yet:

  • The scrape currently replaces the entire database table on every run rather than appending and de-duplicating new reports. A versioning helper for this exists but isn't wired in yet.
  • This dashboard is Phase 1 of the plan — it doesn't yet include per-capita normalization or the geographic maps from my original Tableau version of this project, since those need population and space-launch data I'm still re-sourcing.
